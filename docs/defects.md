# Разбор пяти намеренных дефектов

Все числа получены на версии v1 датасета (1514 строк, 4 репозитория), если не
оговорено иное. Проверки — `make check`.

---

## Дефект 1. Данные утекают в git

**В чём был.** Три независимые дыры в версионировании:

1. `.gitignore` содержал `__pycache__/`, `.venv/`, `dvc_remote/`, `*.html` — и
   ничего про `data/`. Каталог с датасетом был обычным содержимым рабочей копии.
2. В `dvc.yaml` стадия `split` объявляла в `outs` только `data/train.jsonl`.
   `data/val.jsonl` и `data/test.jsonl` не версионировались **ничем**: ни git,
   ни DVC про них не знали.
3. DVC remote не был настроен вообще (`dvc remote list` пуст). Выгружать данные
   было некуда — даже то, что DVC отслеживал, существовало только локально.

**Как проявлялся.** `git add . && git commit` затягивал в историю JSONL целиком;
`git log --stat` показывал крупные файлы. Каталог `data/` весит 5,6 МБ, кэш
источника `sources/` — 7,4 МБ: **13 МБ бинарного мусора в истории git при первом
же коммите**, и это только на v1. Откатить такое можно лишь переписав историю.
Параллельно `dvc push` падал: некуда. А `val`/`test` не восстанавливались вообще
ничем — у соседа после клонирования они бы просто отсутствовали.

**Как исправлен.**

* `.gitignore` — добавлены `data/`, `sources/`, `*.bak`, `*.orig`
  (последние два — следы прогонов `tests/check.sh`).
* `dvc.yaml`, стадия `split` — в `outs` добавлены `data/val.jsonl` и
  `data/test.jsonl`.
* `dvc remote add -d local dvc_remote` — локальный remote рядом с проектом,
  сам каталог в `.gitignore`.
* Кэш выгрузки взят под DVC: `dvc add sources` → `sources.dvc` в git.
  Каталог намеренно лежит **вне** `data/`: `data/` целиком в `.gitignore`, и
  файл-указатель `sources.dvc` оттуда в git бы не попал — git не заходит внутрь
  игнорируемого каталога, и отменить это через `!data/*.dvc` нельзя.

**Чем подтверждается.** `git ls-files data/ | wc -l` = **0**. Все пять путей из
`params.paths` объявлены в `outs` (проверка самопроверки сравнивает их со
списком автоматически). `dvc remote list` → `local`. Проверка 1 зелёная целиком.

## Дефект 2. `dvc repro` не замечает смену версии данных

**В чём был.** Граф был разорван в двух местах:

1. У стадии `collect` не было ни секции `params:`, ни зависимости от источника:
   в `deps` лежали только `src/collect.py` и `src/config.py`. А версия датасета
   живёт именно в `params.yaml` (`collect.version`) — специально, чтобы
   `dvc.lock` помнил, из чего собран артефакт. Раз секция не объявлена, её
   изменение не меняло хеш стадии.
2. Главное: у стадии `clean` в `deps` **не было `data/raw.jsonl`**. То есть
   ребра `collect → clean` в графе не существовало. Даже если бы `collect`
   пересчитался, дальше по графу ничего бы не поехало.

**Как проявлялся.** `python scripts/set_version.py v2 && dvc repro` →
`Data and pipelines are up to date`. В `data/` оставались артефакты от прошлой
версии, метрики — от прошлой версии, и `dvc metrics diff` показывал пустоту.
Самый неприятный класс ошибок: пайплайн ничего не сообщает, просто молча отдаёт
вчерашний результат.

**Как исправлен.** В `dvc.yaml`:

```yaml
collect:
  deps: [sources, src/collect.py, src/commits.py, src/config.py]
  params: [collect, paths.raw]
  metrics: [metrics/collect.json]
clean:
  deps: [data/raw.jsonl, ...]
```

Секция `collect` взята целиком, а не `collect.version`: список файлов-источников
и потолки балансировки влияют на результат ровно так же, как номер версии.
Заодно объявлены `metrics/collect.json` (стадия его писала, а DVC о нём не знал)
и забытая зависимость `clean` от `src/stats.py`, который она импортирует.

**Чем подтверждается.** Проверка 4: `clean.jsonl` пересчитан —
`v1 2f63d594 (1514 строк) → v2 a71a2f45 (2397 строк)`. Хеш и число строк
меняются от одной смены `collect.version`.

## Дефект 3. Контаминация train/test

**В чём был.** `src/split.py` резал набор **по строкам**: функция `row_split()`
тасовала индексы `random.Random(seed).shuffle(order)` и раздавала их по долям.
Ключ группы при этом вычислялся — словарь `sizes` с размерами групп исправно
заполнялся, — и **никуда не использовался**. Второй слой: отчёт о контаминации
`report()` считался, укладывался в `metrics/split.json` и ни на что не влиял.
Стадия завершалась успешно с любым пересечением.

**Как проявлялся.** `scripts/check_contamination.py` находил пересечение по
группам. Сам пайплайн при этом был зелёный: `dvc repro` отрабатывал целиком и
молчал.

**Как исправлен.**

* `row_split()` заменена на `group_split()`: группа (репозиторий) уходит в сплит
  целиком. Раздача жадная — от крупных групп к мелким, каждая в тот сплит, где
  недобор до целевой доли больше; `seed` разрешает только ничьи по размеру.
  Пустой сплит чинится отдельно: в него отдаётся самая мелкая группа из того
  сплита, где групп больше одной.
* Стадия падает при ненулевом пересечении: `if not is_clean(rep): raise SystemExit`,
  предварительно напечатав каждую ненулевую ось и записав метрики — чтобы было
  с чем разбираться.
* Добавлена проверка «групп меньше, чем сплитов»: группу нельзя разрезать
  пополам, не создав утечку, и лучше сказать об этом словами.

**Чем подтверждается.** Замер на одних и тех же 1514 строках:

| ось | случайный сплит по строкам | сплит по группам |
|---|---|---|
| пересечение по id | 0 | 0 |
| пересечение по тексту | 0 | 0 |
| **пересечение по группам** | **4 из 4** | **0** |
| near-dup пар train↔test | 0 | 0 |

Все четыре репозитория, попавшие в test, присутствовали и в train: все 152
строки теста приходили из проектов, чей стиль модель уже видела. Показательно,
что первые три оси при этом нулевые — дублей в коммитах нет, и утечка здесь
целиком стилистическая. Именно такую метрику на test и называют «приятно
удивившей». Проверка 5 зелёная, `groups_by_split` в `metrics/split.json`
показывает непересекающиеся списки.

## Дефект 4. Дедупликация только точная

**В чём был.** В `src/clean.py` шаг 5 существовал только в виде заглушки:

```python
# 5. TODO: сюда просится ещё один шаг дедупликации.
near: set[int] = set()
```

Функция `near_duplicates()` в `src/dedup.py` была написана, оттестирована по
смыслу и **ни разу не вызывалась**. Секция `clean.near_dup` в `params.yaml`
читалась только стадией `split` — ради порога Жаккара для проверки контаминации.

**Как проявлялся.** Пара почти одинаковых примеров — тот же текст с другой
нумерацией и другими пробелами — переживала очистку и оставалась в датасете
дважды. Метрика `dropped_near_dup` при этом честно писалась в
`metrics/clean.json` и всегда равнялась нулю, что выглядело совершенно
правдоподобно: «почти-дублей нет».

**Как исправлен.** Вызов `near_duplicates()` после точной дедупликации —
именно в этом порядке: дешёвая операция снимает основную массу, дорогой
MinHash+LSH работает по остатку. Параметры берутся из `clean.near_dup`
(`shingle_words: 4`, `num_perm: 64`, `threshold: 0.85`).

**Чем подтверждается.** Проверка 2 на синтетике: подложены точный дубль и
почти-дубль (тот же вопрос, `0.` заменено на `0)`, добавлены пробелы). Было:
`dropped_exact_dup = 1`, `dropped_near_dup = 0` — почти-дубль выживал. Стало:
`dropped_exact_dup = 1`, `dropped_near_dup = 1`.

На реальных данных near-dup находит 0 при рабочем пороге 0,85 — и это свойство
источника, а не сломанной проверки. Чувствительность порога на тех же 1514
строках: 0,95 → 0, 0,85 → 0, 0,75 → **2**, 0,60 → **11**. То есть механизм
работает и показывает ожидаемый рост при ослаблении порога; 0,85 оставлен,
потому что обязан совпадать с `contamination.threshold`.

## Дефект 5. Гейт разнообразия — не гейт

**В чём был.** `src/diversity.py` считал все нарушения правильно, а потом:

```python
if failed:
    # TODO: гейт или отчёт?
    print("diversity: предупреждение — " + "; ".join(failed))
```

Исключение `DiversityError` было объявлено в модуле и ни разу не возбуждалось.
Стадия завершалась с кодом 0 при любом числе нарушенных порогов.

**Как проявлялся.** Вырожденный набор — 1200 строк с одним системным промптом,
одной темой и ответами одной длины — проходил **весь пайплайн целиком**: схему,
дедупликацию, гейт, сплит, проверку контаминации. Формально он безупречен:
строки разные, дублей нет, битого JSON нет. Единственным следом оставалась
строчка предупреждения в логе `dvc repro`, где её никто не читает.

**Как исправлен.**

* Нарушения печатаются **по одному в строку** (разбираться придётся с каждым
  отдельно), после чего возбуждается `DiversityError` — стадия падает, `dvc repro`
  останавливается.
* Заодно гейт починен по существу для этой задачи. Пять порогов, завязанных на
  разнообразие ответа, снижены — при классификации по шести классам они меряют
  постановку задачи, а не качество набора (обоснование каждого —
  в `docs/datasheet.md`). Взамен добавлены три порога, которые здесь работают:
  `min_answer_classes` (пропавший класс — дыра в сборе), `max_answer_share`
  (перекос, при котором константный классификатор обыграет модель) и
  `min_user_len_ratio` (разнообразие, которого нет в ответе, обязано быть во
  входе).

**Чем подтверждается.** На вырожденном наборе гейт называет **7 нарушенных
порогов** и завершается ненулевым кодом:

```
  ✗ системных промптов 1, нужно ≥ 3
  ✗ групп 1, нужно ≥ 4
  ✗ крупнейшая группа занимает 100.0% (порог 40%)
  ✗ разброс длин ответа p90/p10 = 1.0, нужно ≥ 1.05
  ✗ 100.0% ответов имеют одну и ту же длину (порог 50%)
  ✗ различных ответов 4, нужно ≥ 6
  ✗ разброс длин входа p90/p10 = 1.02, нужно ≥ 2.0
```

На реальном датасете нарушений 0, стадия проходит (проверки 6 и 7 зелёные).

## Найдено попутно (сверх пяти)

Не входит в задание, но сломало бы работу:

* **`clean` не зависела от `src/stats.py`**, хотя импортирует из него
  `percentile`. Правка в модуле статистики не пересчитывала очистку.
  Исправлено вместе с дефектом 2.
* **Глобальный потолок класса перекашивал репозитории.** Первая версия
  `collect` ограничивала число примеров на класс по всему набору, и потолок
  выбирался в порядке файлов: у `prisma/orm` оказалось **0 коммитов класса
  `fix`** (лимит исчерпали три предыдущих репозитория), у `angular` — 0 `chore`.
  Так как репозиторий здесь — группа сплита, перекос уехал бы прямо в test.
  Потолок переведён внутрь репозитория (`max_per_class_per_repo`); после правки
  у `prisma/orm` 104 коммита `fix`.
* **`prisma/prisma` переименован в `prisma/orm`**, API отдаёт 301. Скрипт
  выгрузки падал с `HTTP 301`; добавлена обработка переадресации в пределах
  `api.github.com`.
