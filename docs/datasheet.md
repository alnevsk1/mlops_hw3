# Datasheet: классификация коммитов по типу Conventional Commits

## Задача

По сообщению коммита **без префикса типа** и по списку изменённых файлов со
статистикой определить тип коммита и флаг breaking change.

* **Вход** — текст сообщения (заголовок + тело) плюс до 10 путей в формате
  `- path | status | +added -deleted`.
* **Выход** — JSON: `{"type": "feat|fix|docs|refactor|test|chore", "breaking": bool}`.
* **Формат** — chat JSONL: `{"id", "topic", "messages": [system, user, assistant]}`.
* **Метрика при обучении** — macro-F1 с матрицей ошибок. Классы несбалансированы
  (самый частый занимает 34%), accuracy здесь ничего не покажет.

Ответ занимает 15–20 токенов, вход при `seq 512` обрезается редко: p90 длины
входа — 1654 символа.

## Источник

Выгрузка GitHub REST API (`GET /repos/{repo}/commits` + `GET /repos/{repo}/commits/{sha}`)
из шести репозиториев, которые последовательно соблюдают Conventional Commits.

| Репозиторий | Лицензия кода | В версии |
|---|---|---|
| `angular/angular` | MIT | v1, v2 |
| `nestjs/nest` | MIT | v1, v2 |
| `vuejs/core` | MIT | v1, v2 |
| `prisma/orm` (бывший `prisma/prisma`) | Apache-2.0 | v1, v2 |
| `nuxt/nuxt` | MIT | v2 |
| `vitejs/vite` | MIT | v2 |

**О лицензиях.** Перечислены лицензии кода репозиториев. Сам датасет состоит из
метаданных истории (сообщения коммитов, имена файлов, числа добавленных и
удалённых строк) — фрагментов кода в нём нет. Метаданные получены через
публичный API без аутентификации к приватным данным. Для учебного использования
этого достаточно; для публикации набора лицензии нужно проверить отдельно,
поскольку авторство сообщений принадлежит тысячам контрибьюторов, а не проектам.

**Снимок.** Выгрузка сделана 20 сентября 2026 года, по 1000 последних коммитов
ветки по умолчанию на репозиторий. Датасет не является случайной выборкой из
всей истории проекта: это срез последних месяцев, и стиль сообщений в нём
современный. Кэш выгрузки лежит в `sources/` и версионируется DVC
(`sources.dvc`), поэтому пересборка не ходит в сеть.

## Что сделано с источником

Выгрузка — это сырьё. Стадия `collect` превращает его в датасет, и каждое
действие видно числом в `metrics/collect.json` (значения для v1):

| Действие | Параметр | Отброшено |
|---|---|---|
| merge-коммиты — склейка, а не авторский текст | `drop_merges` | 374 |
| коммиты ботов (renovate, dependabot) — шаблон | `drop_bots` | 863 |
| revert — содержит чужой префикс в кавычках | `drop_reverts` | 19 |
| релизные бампы `chore(release): x.y.z` | `drop_release` | 74 |
| заголовок не по конвенции | — | 398 |
| тип вне шести классов (`perf`, `ci`, `build`, `style`) | `types` | 155 |
| нет списка файлов (не дотянут из API) | — | 53 |
| балансировка классов и репозиториев | `max_per_class_per_repo`, `max_per_repo` | 550 |

Из 4000 просмотренных коммитов в v1 осталось **1514**.

Кроме отбора:

* **Срезана утечка метки во вход.** Префикс `type(scope)!:` удаляется разбором
  заголовка; строка `BREAKING CHANGE:` вырезается из тела (в v1 — 1 случай,
  счётчик `breaking_notes_stripped`). Без этого флаг `breaking` читался бы
  прямо из входа, а задача выродилась бы в поиск подстроки.
* **Инструкция разведена на 5 вариантов** (`collect.system_prompts`), вариант
  выбирается детерминированно по sha1 от id примера. Модель, обученная на одной
  формулировке, заучивает её как константу и ломается от перефраза.
* **Потолок класса считается внутри репозитория.** Первая версия использовала
  общий потолок на весь набор, и он выбирался в порядке файлов: у `prisma/orm`
  оказалось **0 коммитов класса `fix`** — лимит исчерпали три предыдущих
  репозитория. Так как репозиторий здесь — это группа сплита, перекос уехал бы
  прямо в test и обрушил бы macro-F1 на пустом месте.

## Очистка

Порядок стадии `clean` — схема → длины → ПДн → точная дедупликация → near-dup.

* **Схема** — pydantic, битая строка роняет стадию с номером строки.
* **Длины** — `min_user_chars: 30`, `max_user_chars: 4000`. В v1 не отброшено
  ничего: тело сообщения уже обрезано на `collect` до 1200 символов.
* **ПДн** — замаскировано 444 email и 1 телефон в 370 строках из 1514. Источник
  — трейлеры `Co-authored-by: Name <mail@example.com>` в теле коммита. Маскирование
  идёт **до** дедупликации: две строки, отличавшиеся только адресом, после
  маскирования становятся одинаковыми и обязаны схлопнуться.
* **Дедупликация** — точная 0, near-dup 0 при пороге Жаккара 0,85.

Ноль дублей здесь — свойство источника, а не отсутствие проверки: каждый коммит
описывает отдельную правку. Чувствительность порога на v1:

| порог | найдено near-dup |
|---|---|
| 0,95 | 0 |
| 0,85 (рабочий) | 0 |
| 0,75 | 2 |
| 0,60 | 11 |

Порог 0,85 оставлен рабочим: он совпадает с порогом проверки контаминации
(`contamination.threshold`), а разные пороги ловили бы не контаминацию, а
разницу порогов. Что near-dup действительно работает, проверяется на синтетике
в `tests/check.sh` (проверка 2): тот же вопрос с другой нумерацией вариантов
точная дедупликация не видит, а near-dup удаляет.

## Сплит

`split.group_key: topic`, где `topic` — **репозиторий**. Группа уходит в сплит
целиком.

Почему по репозиториям, а не по коммитам: у каждого проекта свой стиль сообщений
(angular пишет `fix(compiler): ...` с ссылкой на PR, vue — короткие заголовки без
тела). Коммиты одного репозитория в train и test означали бы, что модель учит
стиль проекта, а не задачу, и метрика на test была бы завышена.

| | v1 | v2 |
|---|---|---|
| train | 999 (66,0%) — angular, prisma | 1882 (78,5%) — angular, nuxt, prisma, vite |
| val | 199 (13,1%) — nestjs | 316 (13,2%) — vuejs |
| test | 316 (20,9%) — vuejs | 199 (8,3%) — nestjs |

**Доли не равны заданным 80/10/10, и не могут быть.** Группа неделима, а групп
четыре в v1 и шесть в v2: при четырёх группах любая из них — это минимум 13%
набора. Раздача жадная, от крупных групп к мелким, в сплит с наибольшим
недобором; пустой сплит недопустим, поэтому туда отдаётся самая мелкая группа.
Фактические доли пишутся в `metrics/split.json → ratios_actual`. В v2 доли
заметно ближе к целевым — это ещё один аргумент за расширенную версию.

**Контаминация** проверяется отдельно (`scripts/check_contamination.py`) по
четырём осям, все нули в обеих версиях:

| ось | случайный сплит по строкам | сплит по группам |
|---|---|---|
| пересечение по id | 0 | 0 |
| пересечение по нормализованному тексту | 0 | 0 |
| пересечение по группам | **4 из 4** | 0 |
| near-dup пар train↔test | 0 | 0 |

Замер сделан на v1. Показательно, что случайный сплит по строкам даёт ноль по
первым трём осям и провал по четвёртой: здесь утечка не в дублях (их нет), а
целиком в стиле проекта. Метрика на таком test выглядела бы отлично и врала бы.

## Пороги гейта разнообразия

Пять порогов из выданных снижены. Причина общая: **это классификация, а не
генерация**. Ответ — метка класса, группа — репозиторий; у обеих осей
разнообразие ограничено постановкой задачи, а не качеством сбора.

| Порог | Было | Стало | Почему |
|---|---|---|---|
| `min_groups` | 50 | 4 | Группа = репозиторий. Проектов, честно соблюдающих конвенцию, единицы; 50 групп означали бы 50 проектов, которых в выборке нет. |
| `max_group_share` | 0,10 | 0,40 | При 4 группах доля крупнейшей не может быть ниже 0,25 арифметически. Факт: 33% (v1), 21% (v2). |
| `min_answer_len_ratio` | 1,6 | 1,05 | Длины ответа — 34–39 символов, p90/p10 = 1,15 по определению. Порог оставлен ненулевым: он всё ещё ловит случай «все ответы ровно одной длины». |
| `max_same_length_share` | 0,25 | 0,50 | Шесть классов дают шесть длин ответа; самая частая (`fix`) — 40%. |
| `max_duplicate_answer_share` | 0,30 | 0,999 | При шести классах на 1514 строк показатель равен 0,995 по определению и ничего не измеряет. Оставлен как потолок «ответ ровно один на всех». |

Снижение порога — не отмена контроля. Взамен добавлены три оси, которые на этой
задаче действительно что-то ловят:

| Новый порог | Значение | Что ловит | Факт v1 |
|---|---|---|---|
| `min_answer_classes` | 6 | пропавший класс — это дыра в сборе, а не редкий класс | 8 |
| `max_answer_share` | 0,40 | перекос, при котором константный классификатор обыграет модель | 0,34 |
| `min_user_len_ratio` | 2,0 | разнообразие, которого нет в ответе, обязано быть во входе | 11,7 |

Что гейт по-прежнему ловит, проверяется в `tests/check.sh` (проверка 6):
вырожденный набор из 1200 строк с одним системным промптом, одной группой и
ответами одной длины валит **4 порога** и роняет стадию.

## Ограничения — чего датасет не покрывает

1. **Флаг `breaking` вырожден.** 4 положительных примера из 1514. Как задача
   бинарной классификации это не работает; поле оставлено ради полноты формата
   и как честный показатель редкости явления.
2. **Шум в метках.** `refactor` и `chore` авторы путают сами, `chore` против
   `build`/`ci` — вопрос вкуса конкретного проекта. Потолок качества здесь
   задаётся согласием авторов, а не моделью. Если матрица ошибок покажет
   неразделимость этой пары, схему нужно сворачивать до четырёх классов, а не
   догонять метрику.
3. **Утечка метки во входе снята не полностью.** Префикс и `BREAKING CHANGE:`
   вырезаны, но тип часто всплывает в самом тексте («fix a regression in…»).
   Контроль — rule-based бейзлайн по ключевым словам: подозрительно высокий
   macro-F1 у него означает, что задача выродилась в поиск слова.
4. **Только JS/TS-экосистема.** Все шесть проектов — фронтенд и Node. Стиль
   сообщений в Go-, Rust- или Python-проектах другой, и переносимость не
   проверялась.
5. **Только английский язык** сообщений.
6. **Срез, а не история.** Последняя тысяча коммитов на репозиторий, сентябрь
   2026. Конвенции в проектах меняются; на коммитах пятилетней давности модель
   может вести себя иначе.
7. **Тест — это один репозиторий.** Следствие честного сплита по группам: в v1
   test целиком состоит из `vuejs/core`, где всего 6 примеров класса `feat`.
   Macro-F1 на редких классах будет шумным. Уменьшить шум можно только новыми
   репозиториями — это и есть смысл v2 и дальнейших версий.
8. **Ботовые коммиты выброшены целиком.** Если модель будут применять к живому
   потоку коммитов, dependabot-сообщения она увидит впервые.

## Воспроизведение

```bash
$env:GITHUB_TOKEN = "<token>"   # PowerShell; без токена лимит 60 запросов в час
make fetch                      # выгрузка в sources/, резюмируемая
uv run dvc add sources          # кэш источника под DVC
make repro                      # collect -> clean -> diversity -> split
make check                      # восемь проверок
```

Переключение версий: `make v1` / `make v2`, разница — `make diff`.
